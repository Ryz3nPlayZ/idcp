# V1 to V5

This file records the milestones that got IDCP from transport experiments to a product-shaped same-machine controller.

## V1

Goal:

- establish low-level same-machine transport primitives
- prove local communication overhead is real

Proof:

- `fabric-bench`
- `fabric-core`

## V2

Goal:

- move from transport-only thinking to memory discovery
- prove exact and near-duplicate page families are worth targeting

Proof:

- `memory-lab`
- `idcp-memory`

## V3

Goal:

- define the four-engine model
- integrate flow, memory, placement, and pressure under one system story

Proof:

- `idcp-flow`
- `idcp-placement`
- `idcp-pressure`
- `idcp-bench`

## V4

Goal:

- make the system usable as a product-shaped tool
- support named workload profiles and side-by-side naive vs IDCP simulation

Proof:

- `idcp-system`
- `idcpd plan`
- `idcpd simulate`
- `idcpd bench`

## V5

Goal:

- stop behaving like a one-shot research CLI
- become a persistent controller surface with observable outputs

Delivered:

- `idcpd daemon`
- `idcpd status`
- `idcpd report`
- controller snapshots
- adaptive control actions
- markdown report generation
- live runtime execution
- persisted state under a chosen state dir

Proof:

- daemon writes `latest.txt`, `history.log`, and `report.md`
- report generation works independently
- runtime benchmarks and controller runs are repeatable
- tests cover controller and report behavior

## Finish line for this phase

The phase finish line was:

- a real controller entrypoint
- a stable set of runtime commands
- persisted state and status visibility
- generated documentation artifacts
- full validation with tests and benchmark runs

That finish line is reached.

## Next after V5

- replace more modeled memory and copy behavior with measured runtime effects
- add multi-profile daemon sessions instead of one-profile runs
- add real workload traces and snapshots
- add more realistic contention and tail-latency accounting
- move from profile execution toward runtime-managed worker graphs
